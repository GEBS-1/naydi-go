## Исправления

- Позднее определение города больше не стирает текст, введённый на главной до окончания загрузки. Именно это мешало мобильному сценарию маршрута.
- Добавлена серверная проверка Cloudflare Access JWT через jose: фиксированный доверенный issuer из конфигурации, RS256, подпись JWKS, audience, срок действия, обязательные claims и тип app. Ошибка проверки закрывает доступ.
- Неподписанные identity-заголовки теперь принимаются только dev-режимом. `AUTH_TRUSTED_PROXY=1` больше не включает их в production. Существующая сессия владельца сохранена.
- Добавлены повторяемые локальные скрипты `test-admin-identity.mjs`, `browser-final-acceptance.mjs`, `check-router-billing.mjs`.

## Что настроить владельцу на сервере

1. Сохранить текущие D1/R2 данные; не выполнять seed/reset/import. Это Cloudflare Workers-совместимое приложение: обычный Node/VPS без адаптации bindings не равнозначен текущему runtime.
2. Перед миграциями снять отдельные production D1/R2 backup и проверить восстановление в изолированном окружении. Локальная копия не является production-backup.
3. Для подготовленного способа входа администратора настроить Cloudflare Access на административные страницы, указать `AUTH_ACCESS_ISSUER=https://<ваша-команда>.cloudflareaccess.com`, `AUTH_ACCESS_AUD` и `ADMIN_EMAIL`. Сервер должен получать Access assertion и проверяет её сам. Не защищать всё приложение обязательным входом: поиск покупателей остаётся публичным. Общие owner API должны оставаться доступны владельцам по сессии, а административные действия внутри них проверяют actor.
4. Если Cloudflare Access не используется, НЕ включать доверие к email-заголовкам. Нужен согласованный серверный адаптер другого провайдера; текущая реализация не объявляется универсальной авторизацией для произвольного VPS.
5. Настроить серверные `ROUTERAI_API_KEY`, модели и `API_MONTHLY_LIMIT_RUB`/`API_MAX_CALL_RUB`, HTTPS и корректный origin reverse proxy; не публиковать dev mock. Полный список в `.env.example`.
6. Проверить на своём окружении Secure/HttpOnly cookies, Origin, JWKS-доступ, подделку заголовков, чужие магазины и приватные фото. Подписанные локальные test-токены не подтверждают настройку реального IdP.
7. Сверить резерв, повторить успешный фото-поиск и платный поиск, реальные браузерные ограничения частоты/бюджета. Уточнить доступность и условия использования тайлов/геосервисов.

## Готовность

Для продолжения локального закрытого тестирования — да, с перечисленными ограничениями. Для полноценного публичного запуска — пока нет: сверка расхода и положительный фото-сценарий, карта без отказа подложки, браузерный месячный лимит и проверка реального production identity/runtime остаются открытыми.
