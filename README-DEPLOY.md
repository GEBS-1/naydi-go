# НайдиGo — локальный запуск и передача проекта

Доработан существующий проект. Ничего не развёрнуто на naydigo.prepromo.ru. Рабочий интерфейс — `/`, административное подключение — `/onboarding`. Старые `/design/*` остаются отдельными макетами, не источником данных.

## Что реализовано

- Режим «По дороге»: реальные адресные подсказки, автомобиль/пешком, карта пути, расчет дополнительного времени заезда, фильтры и маршрут через магазин. Настройка, ограничения и проверки — в [JOURNEY.md](JOURNEY.md).
- Общий каталог, поиск по словам/частям/синонимам/категориям/характеристикам; запросы сохраняются в БД без привязки к человеку.
- Магазины и товары, загрузка фотографий, обращения и ответы, права владельца.
- Администратор создаёт магазин без владельца, заполняет контакты, сайт/VK/Telegram/MAX, фотографии, источники и товары.
- Черновики исключены на сервере из каталога, поиска, избранного, обращений и карты. Их фотографии также защищены.
- Персональный предпросмотр без входа: 256-битный случайный токен, в БД только SHA-256, срок 30 дней, отзыв/перевыпуск. Страницы и API запрещают кэширование и индексацию, внешние ссылки не отправляют referrer.
- Публикация требует явного подтверждения согласия, адреса, координат, телефона, источника и товаров. Тестовые товары блокируют публикацию. Подтверждение карточки не подтверждает остатки.
- Приглашение привязано к email, одноразовое, действует 7 дней. Повторный выпуск отменяет старое. Передача прав атомарная. После принятия работает кабинет владельца.
- Приглашение отправляется через почтовую программу кнопкой `mailto:` или копированием ссылки. Автоматической отправки email нет; интерфейс не утверждает, что письмо отправлено.

## Технологии и хранение

Next.js 16, React 19, TypeScript, Tailwind CSS; совместимый runtime Vinext. Сервер собирается в Cloudflare Worker. D1 (SQLite) хранит все данные, R2 хранит фото. В локальном режиме они сохраняются на диске в `.wrangler/state`. Это не данные в памяти и не localStorage. При переносе проекта не удаляйте эту папку без резервной копии.

## Запуск на этой машине

Node.js 22.13+. В папке `naydi-go`:

```sh
npm ci
npm run build
npm run db:local
npm run dev
```

`db:local` идемпотентно применяет две текущие миграции только к локальной базе. Уже заполненную базу не очищает. Не запускайте несколько серверов, одновременно записывающих в одно локальное хранилище.

Создайте `.env.local` на основе `.env.example` и укажите:

```dotenv
ADMIN_EMAIL=seedy@sites.test
```

На этой машине файл уже настроен. Откройте `http://localhost:3000/onboarding`, нажмите вход. Локальная имитация авторизации входит как `seedy@sites.test`; она существует только в dev, проверяет loopback-адрес и удаляет подставленные клиентом заголовки. Это не регистрация реального аккаунта.

Если системный npm повреждён, с уже установленными зависимостями доступны прямые команды:

```sh
node scripts/run-framework.mjs build
node scripts/setup-local.mjs
node scripts/run-framework.mjs dev --port 3000
```

## Пять витрин Казани

В текущей локальной базе уже созданы 5 магазинов и 25 товаров. Все магазины — персональные демо-черновики без владельца, все товары — без подтверждённых остатков. Фотографии не скопированы по решению пользователя: разрешения нет. В интерфейсе это обозначено явно.

- Секретные локальные ссылки: `artifacts/LOCAL-PREVIEWS.md` и `artifacts/local-previews.json` (не коммитить и не публиковать).
- Проверенные данные для повторного импорта: `data/kazan-onboarding.json`.
- Полный список источников и пробелов: `SOURCES-KAZAN.md`.
- Мобильные скриншоты: `artifacts/mobile-*.png`.

Для заполнения новой локальной базы при работающем dev-сервере:

```sh
npm run import:kazan
```

Импорт сохраняет записи через административный API. Повторный запуск не перезаписывает изменения существующих карточек и не дублирует товары; он **перевыпускает** ссылки и отзывает старые. Скрипт намеренно отказывается работать с внешним доменом и опубликованными/переданными витринами.

## Сценарий администратора

1. `/onboarding` → новый черновик → заполнить магазин → сохранить.
2. Добавить товары, источник и дату проверки. Если цена неизвестна — оставить пустой; количество не подтверждать без ответа магазина.
3. Создать персональную ссылку и показать владельцу. Перепроверьте неполные поля из внутренних заметок.
4. После реального согласия указать основание, отметить подтверждение и опубликовать.
5. Указать email владельца, создать приглашение и отправить через почтовую программу.
6. Владелец входит с этим email и принимает управление. После этого он меняет товары и отвечает покупателям в `/#business`.

Для опубликованных предварительно подключённых карточек передача идёт через приглашение, а не обычную заявку «Это мой магазин». Старые справочные карточки сохраняют ручное согласование заявки.

## Проверки

```sh
npm run typecheck
npm run test:search
npm run check:persistence
```

Последняя команда проверяет именно сохранённые пять ссылок, 25 товаров, отсутствие фото и неподтверждённость остатков, отсутствие черновиков и демо-товаров в публичном API. Запускайте её после остановки и повторного запуска dev-сервера.

Полный API-тест выполняется на **локальной собранной версии**, отдельно от dev:

```sh
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js dev --config dist/server/wrangler.json --local --persist-to .wrangler/state --ip 127.0.0.1 --port 3001 --inspector-port 0 --var ADMIN_EMAIL:qa-admin@example.com --var AUTH_TRUSTED_PROXY:1
```

В другом терминале:

```sh
npm run test:onboarding
```

Тест имитирует доверенные идентификаторы только на loopback, создаёт синтетическую QA-витрину, проверяет загрузку/приватность фото, редактирование, запрет публикации тестовых товаров, согласие, одноразовое email-приглашение, чужой доступ, поиск, обращения, ответ, изменение цены/остатка и удаление товара. В `finally` снимает QA-витрину с публикации и отзывает предпросмотр. Пять реальных витрин не меняются. Результат — `artifacts/onboarding-test.json`.

## Развёртывание пользователем

Это **серверный Worker-проект**, не статическая папка HTML. Сборка: `dist/server/index.js`, ресурсы `dist/client`, схема `drizzle/`. Нельзя загрузить старый `out/` на nginx и ожидать работы базы/API.

1. Сделать резервную копию локального хранилища при остановленном сервере.
2. На выбранной Worker-платформе настроить постоянные привязки D1 `DB` и R2 `BUCKET`; применить SQL-миграции `0000`, затем `0001` ровно один раз.
3. Настроить `ADMIN_EMAIL` на рабочий email администратора. Не переносить `.env.local` с тестовым email.
4. **Обязательно настроить доверенную авторизацию.** Текущий `app/chatgpt-auth.ts` использует заголовки `oai-authenticated-user-*` от шлюза Sites. В Sites шлюз проверяет личность. На другом хостинге необходимо заменить этот адаптер своей проверенной сессией либо поставить проверенный auth-шлюз, который удаляет клиентские заголовки и добавляет их только после входа. Сам по себе публичный Worker/Wrangler/обычный nginx эту гарантию не даёт. Не выставлять тестовый сервер в интернет.
5. Перенести БД и объекты R2/локальные загрузки поддерживаемым платформой способом, либо повторить проверенный импорт в целевой среде после настройки авторизации. Локальные токены не появятся в новой пустой БД автоматически.
6. Собрать и опубликовать существующий проект на выбранной платформе, затем проверить API, фото и сквозной сценарий до открытия публике.

Файл `.openai/hosting.json` сохранён от существующего проекта. Никакой новый Site и никакой новый деплой в этой доработке не создавались.

Собранный сервер по умолчанию **не доверяет** заголовкам личности: без `AUTH_TRUSTED_PROXY=1` вход и административные изменения закрыты. Включать эту переменную можно только за проверенным шлюзом из пункта 4, либо в локальном loopback-тесте. Она сама не выполняет проверку личности. Dev включает доверие внутренне только совместно с локальным фильтром заголовков. Не переносите это разрешение на публичный сервер без auth-шлюза.

## Ограничения

- У трёх магазинов координаты не подтверждены; маршрут из черновика открывает поиск точного адреса в Яндекс Картах. Публикация требует заполнить координаты. У двух магазинов координаты взяты с официальных сайтов, но также требуют согласования.
- У Сантехника-Кзн прямой сайт отвечал тайм-аутом: использована индексированная официальная главная страница. Перед публикацией перепроверить цены, артикулы и контакты. Отсутствующие соцсети и часы не придуманы.
- Фото 5 МБ / до 5 на форму; доступны только с правами владельца/администратора, через действующий токен или опубликованную карточку. Неиспользуемые файлы пока не удаляются из R2 автоматически.
- Перед коммерческим запуском нужны лимиты запросов/загрузок, мониторинг, резервное копирование и полноценная проверка прав владельцев. Неизвестные email не верифицируются самим прототипом — это обязанность авторизации.
- Карта — интерактивный Яндекс-виджет и список; геокодер и перетаскивание маркера не подключены. API-ключ не требуется для внешнего маршрута. `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` зарезервирован.
- Поиск без сложной морфологии/опечаток; весь небольшой каталог читается из БД. Импорт Excel/CSV/XML/YML обозначен «Скоро»; контракт адаптеров в `lib/import-contract.ts`.
- Нет автоemail, SMS, оплаты, доставки, кассовых интеграций. Ответы покупателя обновляются кнопкой. Гостевой аккаунт зависит от cookie браузера.
- Старые вымышленные демо-данные остаются отдельно в коде/локальной БД, но больше не засеивают публичный каталог автоматически и исключены из него серверными фильтрами.
