## Что ещё не является завершённой приёмкой

Нужен актуальный браузерный прогон фотографии, маршрута с промежуточной точкой и ошибок/лимитов. Ранее выполненные API-тесты этих функций не заменяют этот прогон.

После сетевого сбоя остался резерв 20 ₽ с неизвестной фактической стоимостью. Защита блокирует следующие платные вызовы. Не обнулять резерв: сначала сверить расход у провайдера либо отдельно согласовать консервативное учётное закрытие с сохранением всей суммы. Бесплатные источники и индекс продолжают работать.

## Подключение первого магазина

1. Владелец открывает «Добавить магазин» (`/connect`) и отправляет контакты с согласием. Это только заявка, не права доступа.
2. Администратор проверяет заявителя в `/connections`, отмечает связь и создаёт закрытую карточку в `/onboarding`.
3. Вносит реальные контакты, подтверждённый адрес и товары с первоисточниками. Не копирует фотографии без разрешения. Отправляет секретный предпросмотр лично владельцу.
4. Получает и фиксирует согласие, проверяет данные и публикует карточку. В текущем механизме приглашение владельца выдаётся после этой проверки/публикации.
5. Отправляет персональное приглашение по проверенному контакту. Владелец принимает одноразовую ссылку и получает серверную сессию.
6. Проверяет с владельцем изменение цены, остатка, фотографии и скрытие товара. Не публикует старые пять закрытых витрин по факту получения новой заявки.

## Порядок безопасного деплоя (только после разрешения)

1. Установить реальные идентификаторы целевого Worker, D1 и R2 существующего хостинга. Локальные placeholder bindings не являются production-настройкой. Не создавать пустую базу взамен существующей.
2. Снять **отдельную production** резервную копию D1 и объектов R2 с манифестом/контрольными суммами. Проверить восстановление в изолированном окружении. Локальный `test-local-restore.mjs` подтверждает только локальную копию и не заменяет этот шаг.
3. Проверить список применённых миграций и diff схемы. Применять только недостающие миграции после backup; не запускать seed/reset/import поверх production.
4. Настроить доверенную авторизацию администратора. Для Cloudflare подходит проверяемый identity-шлюз с проверкой JWT (подпись, issuer, audience), а не доверие присланному клиентом email. Текущие dev mock и `AUTH_TRUSTED_PROXY=1` без такого шлюза недопустимы. Сессии владельца сохраняются в D1; покупатель остаётся без регистрации.
5. Секреты передать серверному окружению: `ROUTERAI_API_KEY`, `ADMIN_EMAIL`. Модель и расходы: `ROUTERAI_MODEL`, `ROUTERAI_WEB_MODE`, `ROUTERAI_WEB_MODEL`, `API_MONTHLY_LIMIT_RUB`, `API_MAX_CALL_RUB`. Полный пример — `.env.example`. Brave не обязателен. Ключи не помещать в клиентские переменные или Git.
6. Для публичного трафика определить допустимую нагрузку и условия геосервисов (`OVERPASS_URL`, `PHOTON_URL`, `VALHALLA_URL`); публичные бесплатные серверы не имеют гарантии доступности. Проверить fallback при отказе.
7. Выполнить `npm ci`, `npm run typecheck`, `npm run build`, проверку клиентских секретов. В staging проверить HTTPS, Secure/HttpOnly cookies, Origin, запрет подмены identity-заголовков, чужие магазин/фото, приватные ссылки и API администратора.
8. Повторить браузерные сценарии на staging, проверить лимит расходов и отказ RouterAI. Только после успешной проверки и разрешения владельца выполнить существующий deployment pipeline. Не запускать `npm run dev` как публичный сервер.
9. После выпуска провести smoke-проверку поиска, сессий и приватных витрин; при ошибке откатить код. Откат схемы/данных выполнять только по отдельному согласованному плану, не стирать новые заявки и товары.

## Действия владельца до публикации

- Подтвердить целевой хостинг, реальные D1/R2 bindings и способ production identity-шлюза.
- Предоставить доступ для production-backup и staging-проверки либо выполнить их самостоятельно.
- Установить серверные секреты и желаемые лимиты расходов; сверить незавершённый API-резерв.
- После приёмки отдельно разрешить production-деплой.
