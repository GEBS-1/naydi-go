# PostgreSQL — the only application database

Local application has been switched from SQLite/D1 to PostgreSQL 17.11.
There is no runtime SQLite fallback. `DATABASE_URL` is mandatory.
All routes use the same PostgreSQL-backed prepared-statement and transaction layer.

## Local launch

- `npm run dev` starts PostgreSQL if needed and opens the app on port 3001.
- `npm start -- --port 3001 --hostname 127.0.0.1` serves the built Node app.
- `npm run db:local` provisions the local cluster if missing, imports legacy data
  ONCE into an empty PostgreSQL DB, and otherwise runs only PostgreSQL migrations.
- `npm run db:migrate` applies PostgreSQL migrations with checksums and an advisory lock.
- `npm run db:backup` creates a native pg_dump and a copy of the photo directory.
- `npm run db:stop` stops PostgreSQL cleanly. Existing records remain on disk.

The official Windows runtime is `.sites-runtime/postgres/pgsql`.
Permanent data is `.sites-runtime/postgres/data`, outside build output.
The loopback-only port is 5433; the application role is not a superuser.
PostgreSQL fsync, full_page_writes and synchronous_commit are enabled.
Windows startup creates a drive alias recorded in `.sites-runtime/postgres/drive.json`
because PostgreSQL bootstrap cannot use this Cyrillic installation path in C locale.
The alias points at the same directory and does not move any files.

`.env.postgres` contains the application connection string. `.env.postgres-admin`
contains local cluster administration credentials. Both are ignored by Git.
Do not remove `.sites-runtime/postgres/data`, `.sites-runtime/photos`, or these
credential files during cleanup. Build output and node_modules can be recreated
without deleting these data directories.

## Completed local migration

All 35 application tables were copied and verified record by record: 19 shops,
74 products. All 55 stored photos were copied and checked by SHA-256.
The source SQLite files remain as a read-only migration fallback for recovery;
the running application does not open or modify them.
Snapshots/reports are under `artifacts/postgres`. Native pg_dump/pg_restore has
been verified by restoring into a separate temporary database and comparing
protected records. The working DB was also restarted and persisted a new write.

Legacy SQL under `drizzle/` is kept only for historical import and fixture tests.
The current schema is `db/schema.ts` (pg-core); new migrations are generated by
`npm run db:generate` into `postgres/migrations`. Review generated SQL before
applying. Applied migrations are recorded in `naydi_migrations`; existing
migration files cannot be silently changed.

## Verification

- `npm run test:seller:postgres`: native PostgreSQL isolated schema; real routes
  for account restrictions, shop/cards/photos, review, publication, nearby search.
- `npm run test:persistence`: restarts the local PostgreSQL server and checks
  existing records plus a newly persisted write. Run while the dev app is up.
- `node scripts/test-postgres-restore.mjs`: restores the latest backup into a
  temporary DB, verifies hashes, then removes only that temporary DB.
- `npm run test:postgres`: isolated PostgreSQL-engine compatibility/import tests.

Telegram/MAX transport is simulated in automated tests. Actual bot callbacks
must be checked separately once public webhook configuration is available.
Both providers share one account/session module; confirmed identities can be
linked from the seller page, preserving the same shop and the 30-day session.

## Production

Production has NOT been switched or deployed as part of this local migration.
Before deploying, provision a PostgreSQL database on the VPS, pause writes,
back up production SQLite and photos, copy a consistent production snapshot
using `scripts/migrate-postgres.mjs` (the CLI records the verified baseline automatically). Never import the LOCAL database
onto production. Set the production `DATABASE_URL` in its runtime.env.
The deployment script now refuses a server without PostgreSQL configuration,
backs up PostgreSQL+photos, and runs only PostgreSQL migrations. Production
should use a service-managed PostgreSQL instance and off-host tested backups.
